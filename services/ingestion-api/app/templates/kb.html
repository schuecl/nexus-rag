rag-ingestIngest role

Submitting documents

Any user holding rag-ingest can submit documents without needing prior approval to begin processing — review happens after, not before.

What this role can do

  • Upload PDF, DOCX, PPTX, XLSX, TXT/Markdown, or HTML, up to 50 MB per file.
  • Select more than one file to submit them as a batch sharing one set of tags — up to {{ max_batch_files }} files at once. Each file is still stored, embedded, and reviewed independently, so one bad file in a batch doesn't block the rest.
  • Tag Classification, Releasability, and Access scope yourself — the choices offered are already constrained to what your own clearance authorizes; the UI won't even show you a level above your clearance.
  • Track your own submissions and get notified of the curator's decision, including the reason if rejected.
  • Supersede an existing approved document instead of creating a duplicate — a single-file submission only, since supersession is one document replacing one other.

Walkthrough

  1. 1
    Open Upload Drag one or more files onto the drop zone, or browse for them from your device. Selecting more than one submits them as a batch sharing the tags below.
  2. 2
    Tag security and access Classification is a single required value. Releasability is one or more checkboxes (e.g. NATO + FVEY) — leave the no-restriction default if nothing applies. Access scope is free text: ALL_AUTHENTICATED, or a comma-separated list of orgs/groups/users allowed to see it regardless of classification/releasability.
  3. 3
    Add document metadata Source/Originator and Document type are required; Program/community and Effective date are optional context for discovery and lifecycle management.
  4. 4
    Optional: link a supersession Paste an existing approved document's ID in "Supersedes document" to submit this as a new version. Checked at approval time against both your own authority and the prior document's. Not available when more than one file is selected.
  5. 5
    Submit A single file is accepted immediately into processing — check the status badge on the Upload page or watch Notifications for the curator's decision. A batch shows each file's own accepted/rejected outcome and status as it moves through processing.
i
Not retrievable yet

A submitted document is parsed, chunked, and embedded right away, but stays invisible to search until a curator in your org approves it — that's the control against a mis-tagged document ever reaching a query. In a batch, each file goes through this independently: shared tags are a submission-time convenience, never a shared curation decision.

rag-queryQuery role

Searching the corpus

Every query is filtered server-side by your own clearance, releasability, and access scope before results ever reach you — there's no client-side filter to bypass, on this page or from LibreChat.

What this role can do

  • Test retrieval directly from this portal's Search page, or through LibreChat's rag_search MCP tool, under the exact same identity and filter.
  • See citations — source document, classification, releasability, and location within the document — alongside every answer.
  • Get an honest "no results" instead of a guess when nothing passes the access filter or the reranker isn't confident.

Walkthrough

  1. 1
    Open Search Enter a question and, optionally, how many results to return.
  2. 2
    Read the results Each hit lists the source document, its classification/releasability, and where in the document the passage came from — verify grounding before trusting an answer.
  3. 3
    Use the production path: LibreChat This Search page is a debugging aid, not a replacement. In LibreChat, add the rag_search MCP tool — it forwards your own Keycloak identity, so you get the identical filter without extra setup.
i
Reranking can fall back

If the reranker service is unreachable, results still come back in fused dense+BM25 order — the response says so explicitly rather than silently changing ranking behavior.

rag-curate:<org>Curate role

Reviewing submissions

Your curation authority is scoped to the org(s) named in your own rag-curate:<org> role(s) — never every submission system-wide, and capped by your own clearance and releasability: you can't approve a document tagged above what you personally hold.

What this role can do

  • See a queue of pending submissions scoped to your org(s), with the tags the uploader assigned.
  • Approve (publishes it — becomes retrievable), reject (with a required reason sent back to the uploader), or correct the Classification/Releasability/Access-scope tags before approving.
  • Browse the List — every document across your orgs, any status, not just what's waiting in the queue — and correct metadata even after a document has already cleared curation, without a new supersession.

Walkthrough

  1. 1
    Open Curation → Queue Everything currently awaiting review in the org(s) you cover.
  2. 2
    Check the tags Correct Classification, Releasability, or Access scope inline before you approve, if the uploader got something wrong.
  3. 3
    Approve or reject Approve makes it retrievable immediately; reject requires a reason, which becomes a notification back to the uploader.
  4. 4
    Use List for anything already decided Search/filter every document in your orgs by status, filename, originator, type, or uploader — and edit metadata on an already-approved document without triggering supersession.
i
Supersession never leaves a gap

Approving a new version makes it retrievable before the old version is removed — there's never a window where neither version is retrievable. Your authority is re-checked against the old document too, since a new version can change its classification.

rag-purgePurge role

Permanent destruction

Destruction authority is deliberately separate from both curation and admin — holding rag-curate:<org> or rag-admin grants no purge authority at all, and vice versa.

What this role can do

  • Delete a document's content everywhere it's stored — with a required reason, fully audited.
  • See the List page's every document, unscoped by org, clearance, or releasability — the same reach as the destruction authority itself.
  • In most deployments, purge is two-person: filing a request and confirming it require two different rag-purge holders — you cannot confirm your own request.

Walkthrough

  1. 1
    Find the document in List As a purge holder you see every document regardless of org — search by filename, originator, type, or uploader.
  2. 2
    File a purge request Nothing is destroyed yet — this only records that you've asked.
  3. 3
    Get a different holder to confirm A second, distinct rag-purge account must confirm before anything is deleted — enforced server-side, not just a UI convention.
  4. 4
    Deletion runs The document's id and a "purged" status survive so prior audit history keeps something to point to, even though the content itself is gone.
i
Single-holder mode exists, but isn't the default

A deployment can disable two-person confirmation for a single-purge-holder dev setup. Production deployments (this Helm chart's default) require it.

rag-adminAdmin role

Portal configuration

rag-admin manages the classification/releasability vocabulary and the portal's own presentation — it grants no document, query, or curation access at all. That boundary is deliberate: the person who manages the tagging vocabulary is not automatically the person who can see what's tagged with it.

What this role can do

  • Set the classification banner (CAPCO-style text and color) shown at the top and bottom of every page.
  • Adjust the portal theme, application name, and logo (also reused as the favicon).
  • Configure the login page's mandatory-acceptance warning banner that a visitor must accept or decline before signing in.
  • Manage the Classification/Releasability controlled vocabularies — today this is API-only (POST/DELETE /admin/classifications, /admin/releasability); there's no form for it on this page yet.

Walkthrough

  1. 1
    Open Admin Every section here writes through its own API route, independently.
  2. 2
    Set the classification banner Text plus a color; clearing it goes back to an explicit "No label set" — never silently "Unclassified".
  3. 3
    Adjust theme and branding Palette, application name, and logo URL — shown on the login page, browser tab, and header.
  4. 4
    Configure the login page's warning banner Title and body text for the mandatory popup a visitor must accept or decline before authenticating.
i
"No label set" is not "Unclassified"

An unset banner deliberately renders "No label set" rather than defaulting to Unclassified — "nobody has configured a marking" and "this system holds unclassified material" are different statements, and this page never conflates them.
